# GoodAI Monitor
## 产品需求说明书（Product Brief）

**版本：** 1.0  
**产品阶段：** MVP（最小可行产品）  
**产品类型：** 网站可用性监控与故障诊断平台  
**目标：** 打造一个真实运行、可持续使用、具备扩展能力的在线服务，同时展示专业的云计算、IT 运维和可靠性工程能力。

---

## 一、产品愿景

我们希望打造一个简单、可靠、易于使用的网站监控平台，让用户能够及时了解自己的网站或在线服务是否正常运行，并在出现问题时获得清晰的故障信息和及时通知。

用户只需注册账户、添加想要监控的网站，系统就会在后台持续执行检查，记录网站的运行状态和响应表现，并在检测到异常时通知用户。

产品不仅要有美观的界面，更必须是一项真正可用的在线服务：用户可以注册、管理监控目标、查看真实的检查记录、接收告警，并在一段时间后回顾服务的运行情况。

## 二、目标用户

产品首先面向以下用户：

1. **个人网站所有者：** 希望知道个人网站、博客或作品集是否正常运行。
2. **小型企业与网站运营者：** 希望及时发现企业网站或线上服务的可用性问题。
3. **独立开发者与 IT 运维人员：** 希望以简单的方式监控多个网站或 API 服务。
4. **技术学习者与小型项目团队：** 希望通过统一的界面了解服务状态、响应时间和故障历史。

MVP 阶段以个人用户和小型团队为主，不以大型企业级监控平台为目标。

## 三、核心用户体验

### 3.1 用户注册与账户管理

用户能够创建自己的账户并安全登录。

登录后，用户只能查看和管理属于自己的监控目标、检查记录、故障事件和个人设置。

用户能够安全退出账户，并在需要时完成密码重置等基本账户操作。

用户不需要具备专业的系统管理知识，就能够完成主要操作。

### 3.2 添加需要监控的网站

用户可以输入一个公开网站或服务的 URL，例如：

- `https://example.com`
- `https://www.example.org`
- `https://api.example.com/health`

系统应当能够识别并验证用户输入的地址，并在确认目标符合安全规则后创建监控任务。

用户可以为监控目标设置一个容易识别的名称，例如“公司官网”“个人博客”或“订单 API”。

用户可以根据自己的需要配置可用的监控选项，例如检查频率、超时时间、预期 HTTP 状态码，以及可选的页面关键词检查。

系统应提供清楚的操作反馈。无效地址、无法访问的目标或不支持的配置应得到明确解释，而不是静默失败。

出于安全和资源管理需要，系统可以限制每个账户能够创建的监控数量和检查频率，并向用户说明适用限制。

### 3.3 持续监控

创建监控任务后，系统应在后台持续执行检查，不要求用户保持浏览器打开，也不要求用户手动启动每次检查。

系统应根据用户选择的检查频率，定期验证目标的可用性。

基础检查至少应覆盖：

- DNS 解析结果及相关解析错误。
- 网络连接与连接超时。
- HTTPS/TLS 连接及证书相关异常。
- HTTP 响应状态码。
- 响应时间。
- 用户启用的页面内容或关键词检查。

系统不能仅凭 HTTP 返回码就断定一个网站完全正常或已经彻底宕机。

检查结果应明确区分成功、失败、超时和其他无法确定的情况。对于无法确认的结果，不应误报为已经证实的故障。

系统应尽可能提供可理解的失败原因，并保留足够的信息供用户进一步排查。

### 3.4 监控仪表盘

登录后的首页应让用户快速了解所有监控目标的整体情况。

仪表盘至少应展示：

- 监控目标总数。
- 当前正常、异常或未知状态的目标数量。
- 每个目标最近一次检查的结果。
- 最近的响应时间。
- 一段时间内的可用率或成功检查比例。
- 最近发生的故障事件。
- 需要用户关注的异常。

所有展示的数据必须来自真实的检查结果和系统记录。

在没有足够历史数据时，应明确展示数据不足，不得使用虚构数据伪装为实际运行结果。

界面应简洁、清晰，适合在桌面浏览器和手机浏览器中使用。

### 3.5 监控详情与历史记录

每个监控目标都应有独立的详情页面。

用户可以查看：

- 当前状态。
- 目标地址与监控配置。
- 最近检查时间。
- 每次检查的成功或失败结果。
- HTTP 状态码、响应时间和相关错误信息。
- 响应时间的历史趋势。
- 可用率及其统计时间范围。
- 历史故障及恢复记录。

用户应能够选择合适的时间范围查看历史数据，并能够区分当前故障与已经恢复的历史事件。

统计结果应说明其计算依据，避免把单次成功检查误认为长期可用。

### 3.6 故障事件管理

当监控结果表明某个目标可能出现故障时，系统应根据明确的判断规则决定是否创建故障事件。

系统应能够记录：

- 故障首次确认的时间。
- 故障类型及相关检查结果。
- 故障持续时间。
- 恢复时间。
- 从故障发生到系统检测并确认异常所经历的时间。

为了降低偶发网络波动造成的误报，系统应支持合理的连续失败确认机制。

当目标恢复正常时，系统应自动更新故障事件状态，并保留完整历史记录。

用户不应因为短暂的一次检查失败，就收到大量重复告警。

### 3.7 邮件通知

用户可以配置自己的通知邮箱，并选择是否接收故障与恢复通知。

系统至少应支持：

- 新故障确认后的通知。
- 故障恢复后的通知。
- 必要的告警状态说明。

邮件内容应包括目标名称、故障时间、检测到的问题以及查看详细记录的入口。

系统应尽量避免重复发送相同告警，并能处理邮件发送失败等情况。

邮件通知功能应在真实配置邮件服务后进行端到端验证。未实际发送成功的通知，不得被标记为已经送达。

### 3.8 监控管理

用户可以在一个统一的页面管理自己的监控目标，包括：

- 添加新目标。
- 查看目标状态。
- 编辑监控配置。
- 暂停和恢复监控。
- 删除监控目标。
- 搜索或筛选目标。
- 查看相关故障与历史记录。

暂停监控后，系统不应继续按照正常运行状态计算该目标的可用率。统计规则应清晰、一致，并向用户说明。

删除目标时，应有明确的确认机制，并妥善处理相关历史数据。

### 3.9 公开状态页

产品可以提供可选的公开状态页，让用户分享其指定服务的运行情况。

公开状态页应由用户主动创建或启用。

用户只能公开自己明确选择的信息，不能意外泄露内部配置、敏感错误详情、账户信息或其他用户的数据。

公开状态页可以展示服务当前状态、近期故障和历史可用性概况。

如果公开状态页未纳入首个 MVP，产品架构和后续计划应为其保留合理的扩展空间。

## 四、产品可靠性与安全要求

产品本身必须足够可靠，才能为其他网站提供监控服务。

### 4.1 持续运行

监控任务应由后台系统执行，而不是依赖用户当前是否在线。

应用重新启动后，应能够恢复正常工作，不应因为进程重启就永久丢失待执行任务或历史记录。

系统应具备必要的日志、错误处理和健康状态检查能力。

### 4.2 数据保护

用户账户、监控配置、检查记录和故障历史应得到合理保护。

用户只能访问授权范围内的数据。

密码、会话凭证、密钥及其他敏感信息不得被不当记录或公开。

系统应具备合理的数据备份与恢复方案，并能够通过实际测试验证备份是否可用。

### 4.3 安全监控目标

由于用户可以提交任意 URL，系统必须防止监控功能被滥用为访问内部网络、云平台元数据接口或其他受保护资源的工具。

系统应严格限制允许访问的目标地址，处理 DNS 解析变化和重定向风险，并控制检查频率、并发数量、超时时间和响应数据大小。

不符合安全规则的目标应被拒绝，并向用户提供适当说明。

### 4.4 资源与滥用控制

产品应能在预定的服务器资源范围内稳定运行。

系统应具备基本的请求频率限制、监控数量限制和异常任务处理机制，避免单个用户或异常任务消耗过多资源。

产品不得依赖无限制的后台任务或无上限的历史数据增长。

具体资源预算、默认监控间隔和历史数据保留期限，由产品经理根据实际环境与可靠性目标提出方案。

## 五、产品界面与品牌要求

产品应具备一致、专业、现代化的视觉风格，体现可靠性、清晰度和可信度。

所有面向用户的正式界面使用自然、准确的英文，包括页面标题、按钮、状态标签、错误提示、表单说明和邮件通知。

界面应避免不必要的复杂术语。对于 DNS、TLS、HTTP 等专业错误，应提供简短易懂的解释，同时保留供技术人员查看的详细信息。

页面应适配桌面和移动设备，并考虑加载状态、空数据状态、错误状态、无权限状态及操作成功反馈。

产品应具备完整的导航结构。访客可以了解产品用途；登录用户可以方便地进入仪表盘、监控管理、故障事件和个人设置。

## 六、AI 故障分析的未来方向

未来版本可以加入 AI 辅助故障分析。

AI 可以根据真实的检查记录、响应时间变化、DNS/TLS/HTTP 错误及用户提供的脱敏日志，生成：

- 已确认的事实。
- 值得调查的可能原因。
- 建议的验证步骤。
- 下一步排障方向。

AI 必须区分已确认事实和推测，不得把推测包装成已经验证的结论。

AI 不应自动执行服务器命令、修改生产配置、重启生产服务或执行数据库修复。

AI 故障分析不应成为第一版上线的前置条件。应先确保基础监控、历史记录、故障事件和告警机制真实可靠，再决定其具体范围。

## 七、MVP 的交付范围

第一版必须形成一项真实可用的完整服务，而不只是静态页面或功能演示。

MVP 至少包含：

1. 用户注册、登录和安全的数据隔离。
2. 监控目标的创建、查看、编辑、暂停、恢复和删除。
3. 后台定期执行的 HTTP/HTTPS 监控。
4. DNS、连接、TLS、HTTP 状态码、超时和响应时间等基础检查。
5. 可选的关键词检查。
6. 真实的监控仪表盘与历史记录。
7. 故障事件创建、持续时间和恢复记录。
8. 邮件故障告警及恢复通知。
9. 用户设置和必要的账户安全功能。
10. 基本的日志、健康检查、备份、恢复和安全控制。
11. 完整的英文用户界面和基本移动端适配。
12. 可重复执行的自动化测试与可验证的部署流程。

公开状态页可以根据工作量决定是否纳入 MVP，但必须明确记录决定。

AI 分析、付费订阅、多团队协作、高级 API 业务断言、多地区探测节点和企业级权限系统均不属于首版必需范围。

## 八、产品成功标准

MVP 是否成功，应根据真实可验证的结果判断，而不是依据完成了多少页面或代码文件。

至少应满足以下条件：

- 新用户能够完成注册、登录并添加一个合法的公开网站。
- 系统能够在后台按设定频率持续检查该网站。
- 用户能够查看真实的检查记录与响应时间。
- 当测试目标出现可复现的异常时，系统能够根据预定规则记录故障。
- 当测试目标恢复时，系统能够记录恢复过程。
- 邮件故障通知与恢复通知能够在真实测试中成功发送。
- 不同用户之间的数据隔离经过验证。
- 常见的无效 URL 和受限网络目标会被正确拒绝。
- 应用重新启动后能够恢复正常监控。
- 数据备份和恢复流程经过实际验证。
- 自动化测试与部署检查具有可追溯的执行结果。
- 任何未实际验证的能力都明确标记为未验证，而不是宣称已经完成。

具体的可用率目标、响应时间目标、资源上限和测试阈值，应由产品经理结合实际服务器能力提出，并经项目负责人批准后写入正式 PRD。

## 九、对产品经理的要求

本文件定义的是产品目标、用户需求和业务范围，不是最终技术设计。

PM Agent 应在本文件基础上完成以下工作：

1. 明确目标用户、典型使用场景和核心用户旅程。
2. 将每项 MVP 功能拆解为用户故事。
3. 为每个用户故事制定清晰、可测试的验收标准。
4. 设计页面清单、导航关系、表单、状态展示和关键交互。
5. 定义监控状态、故障确认、恢复、可用率统计和告警的用户可见行为。
6. 提出监控间隔、账户配额、历史保留期限和资源预算的建议，并说明依据。
7. 与架构设计保持一致，识别产品需求中的技术依赖和安全风险。
8. 区分 MVP、后续版本和暂不实施的功能。
9. 为开发团队生成可独立实施、可独立测试的任务。
10. 在任务启动前列明范围、依赖、验收标准和需要项目负责人批准的决定。

PM Agent 不得擅自把未批准的功能加入 MVP，不得自行宣称尚未实现或验证的能力已经完成。

遇到需求冲突、技术限制、成本变化或重大安全决策时，应提出具体选项、优缺点和推荐意见，等待项目负责人确认。

## 十、最终产品定义

GoodAI Monitor 是一个面向个人网站所有者、小型企业和技术人员的网站可用性监控平台。

用户通过一个统一、易用的网页管理自己的监控目标，后台持续检查网站运行状态，保存真实历史数据，在发生故障时及时通知用户，并帮助用户理解故障现象。

第一版的首要目标是建立一个真实运行、可靠、安全、可验证的完整产品。后续再逐步增加更深入的诊断、AI 辅助分析和高级功能。

产品最终应当既能解决真实用户的问题，也能够作为一项可以实际演示的工程项目，展示从产品设计到可靠部署和持续运维的完整能力。
